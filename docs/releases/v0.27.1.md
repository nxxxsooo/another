## Installed-binary live leak check

- Used Homebrew's installed `/opt/homebrew/bin/another` (`0.27.1`), not
  `go run`, a test helper, or the repository build.
- Seeded one synthetic Pi session in isolated temporary provider/config/cache
  roots and ran `another rename <synthetic-id> --from pi --auto --dry-run
  --refresh`, with OpenCode as the title agent. A narrow wrapper restored the
  original OpenCode config/cache environment before execing the installed
  OpenCode CLI, so it used the existing shared service, PID `47888`.
- Result: `1111｜Fix｜Temporary Title Service Leak`. The synthetic source file
  remained byte-for-byte unchanged; no real session was read or renamed.
- Direct MCP children of PID `47888`, counted by cwd through `lsof`, were
  **76 before → 76 after**. No titler MCP set was present in either snapshot.
  Run and disposal both used `another-titler-3872100530`; afterwards its
  directory, cached location, and MCP processes were absent.
- No service restart, process signal, tag move, or force push was used.
  The lower baseline than the earlier development check reflects external
  shared-service activity, not cleanup performed by this release workflow.

## Known limitations

- OpenCode's disposal API is experimental and verified live on 2.2.7 only.
  Unsupported versions and cleanup failures return an error; there is no
  silent fallback or retroactive disposal of unrelated/old locations.
- Native Windows automated behavior passed CI; live Windows/Linux OpenCode
  service disposal was not exercised. Other agent regressions use fixtures,
  not live handoffs or title-model calls.
- `make install` initially could not inspect interactive zsh because the
  terminal proxy tried to enter raw mode without a TTY. Existing aliases were
  subsequently verified by actually executing them with terminal-detection
  environment variables removed in that subprocess. No shell config changed.
- Unrelated portfolio `PRODUCT.md` remains untracked and was not committed.
