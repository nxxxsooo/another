# 各 agent 的行为说明

English: [`providers.md`](providers.md)

能力对照表在 [README](../README.md#支持的-agent)。这一页解释表里那些容易让人意外的格子，以及背后每个 agent 的真实行为。

## `—` 是什么意思

`—` 表示这个 agent 没有经过验证的原生操作契约。重命名、归档、换目录和删除都直接修改对应 agent 的原生状态，不是 Another 私有标记；Another 只展示当前 agent 真正支持的操作，不会维护一份刷新后消失的私有状态。

Antigravity 的归档就是这样一格：它的存储里根本没有归档这个状态——标注文件只有标题一个字段，旧摘要表也没有对应的列——补上它只能靠 Another 自己记一份，所以这格留着。

## 删除能不能撤销

取决于会话归谁所有，确认框会在你按下之前说清楚是哪一种。

- **Claude Code 和 Pi**：一个会话就是一个文件，Another 会先把这份字节留在手里，按 `u` 原样写回：session ID、路径、修改时间都不变，agent 恢复它就像从没删过。
- **OpenCode 2**：删除由服务端执行，把对话通过 API 推回去只会得到一个新 ID 的新会话——那是复制不是撤销，所以这里没有撤销，弹窗也如实这么写。
- **Antigravity**：一个会话不是一个文件，而是一整个 brain 目录加一份轨迹数据库，动辄几十兆，Another 不会把这么多字节攥在内存里等你反悔，所以这里同样没有撤销。
- **Qwen Code**：一个会话是一份转录，加上跟着它的那几个 sidecar，还有它编辑过的每个文件的备份，理由同上，删除就是删除。
- **CodeM**：一个会话是一份转录，加上 CodeM 在旁边给它开的工作目录——草稿和工具结果都在里面，理由同上，删除就是删除。

撤销机会只在当前列表内有效：Another 不留自己的回收站，按 `Esc` 即刻放弃，如果 agent 已经往同一路径写了新内容，也绝不覆盖。

## Codex

**三处标题**。Codex 把会话名存了三处：CLI 的线程库、旧版 Desktop 的 `session_index.jsonl`，以及 Codex Desktop 侧边栏实际读的 Electron 状态。重命名三处全写。Desktop 运行时会整份重写自己的状态，写在它下面不是丢改动就是丢它没落盘的东西，所以这种情况不硬写：CLI 侧已经改名，界面会明说侧边栏要等 Desktop 重启才更新，而不是把这次重命名报成失败。

**子 agent 会话**。Codex Desktop 派生出的子 agent 会话（fork 线程）只把回答写成 `event_msg`，没有 `response_item` 那一份，用户角色的记录也只剩注入的插件清单。这类会话能正常打开和迁移；它们没有属于自己的提问，标题就取 Codex 记的子 agent 身份，例如 `api_definitions · Wegener the 9th`。

**消息数**。Codex 每轮对话在 rollout 里最多写两遍，列表里的消息数以前把这两份分开数。现在这个数字和会话真正打开时的条数一致，所以升级后 Codex 会话的消息数可能变小。索引会在升级后第一次运行时把 Codex 重新汇总一遍，不需要手动操作。

## Qwen Code

**归档就是一次移动**。Qwen Code 的转录里没有「已归档」这个字段，它把归档会话放在项目自己的 `chats` 目录下的 `archive` 子目录里，会话列表把这两个目录读成两种状态。Another 的归档就是照做这次移动，sidecar 一起走，所以一个会话从两边的列表里同时消失，取消归档拿回来的也是同一个文件，不是副本。

**删除清掉整个会话**。转录（在哪个状态就删哪个）、worktree / PR / prompt ledger 三个 sidecar、`qwen sessions ps` 读的 runtime sidecar、这个会话编辑文件时留下的备份，以及它在项目置顶分组存档里的那条记录——和 Qwen Code 自己删除时清的是同一批。

**正在运行的会话会被拒绝**。Qwen Code 用转录旁边的 runtime sidecar 标记活着的会话，并且拒绝归档这样的会话；Another 读同一份 sidecar，归档和删除都拒绝——进程正在往这个文件追加内容，把文件从它下面挪走会丢掉正在进行的这一轮。sidecar 如果是另一台机器写的，一律按「活着」处理：本机的 pid 说明不了那边的进程。

## CodeM

**会话属于哪个目录，目录名是一段哈希**。CodeM 把转录放在「会话启动目录的 sha256 前 16 位十六进制」命名的目录下，`codem --resume <id>` 也只在当前工作目录的哈希里找。所以 Another 给出的恢复命令一定以 `cd` 开头：换个目录执行只会直接报错，不会打开别的会话，更不会新建一个。这也是为什么会话归属的目录要从转录自己的 header 里读，而不是从路径反推——哈希不可逆。

**换目录因此缺席**。把会话挪到另一个目录，意味着把文件挪进另一段哈希并改写 header。CodeM 自己没有这个操作，Another 不会替它发明一个。

**重命名和归档都是原生能力**。当前 CodeM 会把 `/rename` 持久化为转录中的 `session_renamed` 记录，归档则会把转录移入项目的 `archived/` 目录。Another 读写同一种记录，也执行同一种可逆移动，不保存私有别名或归档标记。

如果会话原来记录的工作目录已被移动，或变成物理路径哈希不同的符号链接，CodeM 的默认查找无法再从该目录找到旧转录。Another 现在会通过一个只指向原项目哈希目录的 `LINCO_SESSIONS_ROOT` 桥接，让 CodeM 自己读取并继续写入原转录和 scratchpad；其他项目哈希下的同名 ID 不会暴露给它。

**注入的对话轮不会被带走**。CodeM 会把加载的 skill 和提醒当作完整的用户消息写进会话，外面包一层 `<system-reminder>`。那是 CLI 在跟自己的模型说话，不是人说的话，迁移时留在原地。

**飞书客户端发起的会话就是普通会话**。从飞书发起的对话写进同一个存储，id 形如 `sess_feishu_p2p_…`，一样能列出、打开、迁移。存储根目录下那些散着的 `sess_*.json` 是客户端自己的会话记录，不是转录，不会被索引。

## 子会话

子会话默认不在列表里，因为可以从父会话走到它。父会话已经不在索引里时这个前提就不成立了，这类子会话会直接显示在列表中——否则只有知道 ID 才找得到，和丢了没区别。父会话重新出现后它自动回到子会话。完全没有记录父会话的子线程保持隐藏：Codex 的 guardian 线程就是这样，它们是对某次请求动作的机器评估，不是谁的对话。

## 目录已不存在的会话

会话所在目录已经不存在时，行内会标出来——重整过工作区之后，这类会话仍能浏览和迁移，但恢复命令会落在一个不存在的路径上。
